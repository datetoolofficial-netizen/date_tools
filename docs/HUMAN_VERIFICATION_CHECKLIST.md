# سجل الاختبارات البشرية والحسابات الخارجية

آخر تحديث: 2026-09-24

هذا الملف هو المرجع الوحيد لحالة الاختبارات التي لا يستطيع الاختبار البرمجي إثباتها وحده. لا تُسجل فيه كلمات مرور أو رموز تحقق أو رموز استعادة أو مفاتيح API أو أرقام دفع.

## حالات البنود

- `[ ]` لم يبدأ.
- `[>]` جارٍ التحقق منه مع المستخدم.
- `[x]` مكتمل بدليل وتاريخ.
- `[E]` يحتاج حسابًا خارجيًا أو جهازًا فعليًا.
- `[P]` يحتاج خطة مدفوعة أو قرار تكلفة.
- `[B]` متوقف بسبب مانع موثق.

## قواعد الأمان أثناء الاختبار

1. لا يرسل المستخدم كلمة المرور أو رمز التحقق أو رمز الاستعادة إلى المحادثة.
2. لا تُلتقط شاشة تحتوي سرًا أو رمز QR أو بريدًا شخصيًا غير لازم.
3. يكفي توثيق الحالة، طريقة الحماية، عدد المالكين، والتاريخ.
4. أي زر ينشئ مفتاحًا أو يغير صلاحية أو يفعّل خدمة مدفوعة يحتاج تأكيدًا عند لحظة التنفيذ.
5. نراجع أولًا ثم نعدل؛ لا نحذف مستخدمًا أو Token قبل التأكد من وجود طريق دخول بديل.

## جرد MFA والحسابات الحساسة

لم يوجد في `PROJECT_MEMO.md` حتى تاريخ هذا السجل دليل يحدد حسابًا بالاسم على أنه اجتاز MFA. لذلك لا نعتمد الذاكرة، ونبدأ بالحالة `غير موثق` حتى نرى صفحة الأمان.

### H-MFA-01 حساب Google الأساسي

- الحالة: `[x]` مكتمل بتاريخ 2026-09-15؛ التحقق بخطوتين مفعّل، ويوجد مفتاحا مرور وAuthenticator وGoogle Prompt، وأكد المستخدم حفظ رموز الاستعادة خارج الجهاز وإضافة بريد استرداد موثوق.
- الدليل الآمن: حالة الوسائل وتأكيد المستخدم فقط؛ لم تُفتح الرموز ولم يُسجل عنوان الاسترداد أو أي قيمة حساسة.
- يغطي عادةً: Firebase، Google Cloud، Search Console، AdSense، Gmail المرتبط، وملف الدفعات إن كانت الخدمات على الحساب نفسه.
- المطلوب: Passkey أو مفتاح أمان أو تطبيق Authenticator؛ لا نعتمد SMS وحده إن أمكن.
- المطلوب: وسيلتان آمنتان على الأقل، ورموز الاستعادة محفوظة خارج الجهاز الحالي.
- الدليل الآمن: `مفعّل/غير مفعّل`، أنواع الوسائل فقط، تاريخ الفحص، وهل يوجد حساب استرداد موثوق.

### H-MFA-02 حساب Google الاحتياطي أو المالك الثاني

- الحالة: `[E]` غير موثق/وجوده غير مؤكد.
- المطلوب: حساب شخص موثوق مستقل، MFA خاص به، ولا يشارك كلمة مرور الحساب الأساسي.
- لا يمنح كل الصلاحيات تلقائيًا؛ تراجع صلاحيات كل خدمة أدناه.

### H-MFA-03 Cloudflare

- الحالة: `[x]` مكتمل بتاريخ 2026-09-15؛ المصادقة الثنائية مفعّلة عبر مفتاح أمان وTOTP والبريد، وأكد المستخدم حفظ رموز Cloudflare الاحتياطية خارج الجهاز الحالي.
- الجلسات: الجلسة الحالية وجلسة Windows أقدم مرتبطة على الأرجح بمتصفح العمل المستخدم في الفحص السابق، وأكد المستخدم معرفتها؛ لم تُلغ أي جلسة.
- الدليل الآمن: حالة وسائل الحماية وعدد الجلسات وتأكيد المستخدم فقط؛ لم تُفتح الرموز ولم تُسجل عناوين IP أو قيم حساسة.
- المطلوب: MFA آمن لكل عضو بشري، رموز استعادة خارج الجهاز، ومراجعة الجلسات والأجهزة.
- الحساب البشري منفصل عن API Token؛ الـToken لا يستخدم MFA ويجب أن يكون محدود الصلاحية والنطاق.

### H-MFA-04 GitHub

- الحالة: `[x]` مكتمل بتاريخ 2026-09-15؛ التحقق بخطوتين عبر Authenticator مفعّل، ويوجد Passkey واحد، وأكد المستخدم حفظ رموز استعادة GitHub خارج الجهاز الحالي.
- طريقة الدخول: حساب Google المحمي مرتبط، ويوجد بريد موثّق، وتوجد جلسة ويب واحدة هي الجلسة الحالية فقط.
- الدليل الآمن: حالة وسائل الحماية وعدد الجلسات وتأكيد المستخدم؛ لم تُفتح الرموز ولم يُسجل البريد أو أي بيانات جلسة حساسة.
- المطلوب: 2FA آمن لكل مالك أو مساهم، Passkey/مفتاح أمان مفضل، ورموز استعادة خارج الجهاز.
- عند استخدام Organization: تفعيل إلزام 2FA بعد التأكد من أن جميع الأعضاء مستعدون حتى لا يفقد أحد الوصول.

### H-MFA-05 مسجل النطاق وDNS

- الحالة: `[x]` اكتمل فحص Name.com بتاريخ 2026-09-16؛ قفل النقل وWHOIS Privacy وAuthenticator والتجديد التلقائي كلها مفعّلة، والانتهاء في 2027-03-15.
- الفوترة: تحققت وسيلة دفع افتراضية وعملة تجديد بتاريخ 2026-09-16 دون تسجيل التفاصيل، واختفى `Action Required` وأصبحت حالة `Automatic Renewal` مفعّلة.
- الاسترداد والتنبيه: استرداد كلمة المرور عبر البريد مفعّل، وإشعارات نجاح وفشل تسجيل الدخول مفعّلة منذ 2026-09-16.
- محاولة التحقق بتاريخ 2026-09-15: أكد المستخدم إكمال الخطوة، لكن صفحة الإدارة بعد إعادة التحميل ما زالت تعرض `Setup Authenticator App` ولا تعرض وسيلة Authenticator مفعّلة؛ لذلك لم يعتمد البند كمكتمل.
- إعادة التحقق النهائية بتاريخ 2026-09-15: ظهرت وسيلة Authenticator ضمن `Your Current Credentials` وتوفر رابط رموز الاستعادة، وأكد المستخدم حفظ الرموز؛ اعتمد جزء MFA مكتملًا دون فتح الرموز.
- الاعتماد: H-MFA-05 مكتمل بالكامل؛ تتحقق حماية بريد الاسترداد نفسه ضمن H-MFA-06.
- المطلوب: MFA، قفل النطاق، حماية نقل النطاق، بريد استرداد مستقل، وتجديد تلقائي مع وسيلة دفع صالحة.

### H-MFA-06 بريد العمل وبريد الاسترداد

- الحالة: `[x]` اكتمل بتاريخ 2026-09-19؛ البريد الأساسي محمي بوسائل تحقق متعددة، وأكد المستخدم تفعيل التحقق بخطوتين للبريد الاحتياطي وحفظ رموز استرداده خارج الجهاز.
- الدليل الآمن: تأكيد المستخدم وحالة حماية البريد الأساسي؛ لم تُفتح رموز البريد الاحتياطي ولم يُسجل عنوانه أو أي سر في ملفات المشروع.
- ملاحظة الاستمرارية: البريد الاحتياطي مستقل ومحمي، لكن إضافة مالك بشري احتياطي موثوق للمنصات تظل ضمن مراجعة H-IAM ولا تُستبدل بمجرد بريد الاسترداد.
- المطلوب: MFA، وسائل استعادة حديثة، وعدم استخدام بريد شخص واحد كنقطة فشل وحيدة.

### H-MFA-07 حساب مالك المنصة داخل `/admin_login`

- الحالة: `[E]` دور `platform_owner` مطبق برمجيًا، لكن عامل دخول ثانٍ داخل التطبيق غير مثبت.
- المطلوب: تحديد دعم Firebase Authentication لـMFA في الخطة الحالية ثم تفعيل عامل ثانٍ إلزامي للمالك والمدير العام ومسؤول الأمن.
- حسابات المعلنين: MFA إلزامي لمالك المنظمة والمالية عند إضافة الدفع، واختياري موصى به لبقية الأعضاء.

### H-MFA-08 خدمات مستقبلية

- الحالة: `[E]` عند إضافتها.
- تشمل: مزود الدفع والبنك والبريد الإرسالي ومصدر الطقس المدفوع وApple Developer وGoogle Play.
- المطلوب: MFA لكل من يغير الفوترة أو المفاتيح أو الإصدار.

ملاحظة: Service Accounts وAPI Tokens لا يمكن حمايتها بـMFA؛ حمايتها تكون بأقل صلاحية، التخزين السري، التدوير، مدة قصيرة عند الإمكان، وسجل الاستخدام.

## مراجعة الصلاحيات الخارجية

### H-IAM-01 Cloudflare

- الحالة: `[~]` فُحص بتاريخ 2026-09-19 قراءة فقط؛ الضوابط التقنية سليمة، وبقي قرار المالك الاحتياطي واتصال Wrangler.
- الأعضاء: عضو بشري واحد نشط فقط، بدور `Super Administrator - All Privileges`، والتحقق بخطوتين مفعّل.
- الجلسات: جلسة Chrome الحالية فقط؛ لم تظهر جلسات أخرى غير معروفة.
- الرموز: لا توجد Account API Tokens، ويوجد User API Token واحد مخصص للبناء بسبع صلاحيات محدودة لـWorkers وKV وR2 وRoutes مع قراءات الحساب والعضوية اللازمة، دون الفوترة أو إدارة الأعضاء.
- R2: الحاوية الوحيدة `datetools-media` مرتبطة بالـWorker `datetools` باسم `MEDIA_BUCKET` عبر Binding مباشر؛ لا توجد R2 API Tokens مستقلة ولا مفتاح S3 داخل التطبيق.
- CI: GitHub Actions الحالي يشغل الجودة وفحص ما بعد النشر فقط ولا يحتوي سر Cloudflare أو أمر نشر؛ Cloudflare Builds يستخدم رمز البناء المحدود، ولم يُعثر على استخدام لـGlobal API Key في المستودع.
- سجل التدقيق: آخر 7 أيام عرض 31 عملية ناجحة و0 فاشلة؛ الأحداث البشرية المرئية كانت نشرًا عبر الرمز المحدود أو OAuth، والباقي تغييرات نظام للشهادات وDNS.
- تطبيقات OAuth: اتصال Wrangler واحد واسع الصلاحيات للاستخدام التفاعلي المحلي؛ إبقاؤه مقبول فقط مع استمرار الحاجة إليه، وإلغاؤه يتطلب موافقة مستقلة بعد التأكد من عدم الحاجة.
- المتبقي: إضافة مالك احتياطي موثوق عند توفره، واتخاذ قرار موثق بشأن إبقاء اتصال Wrangler أو إلغائه.
- المالك الأساسي والاحتياطي فقط: `Super Administrator - All Privileges` عند الحاجة لاستمرارية الملكية.
- مسؤول التشغيل اليومي: `Workers Platform Admin` بدل Super Administrator عندما لا يحتاج العضوية أو الفوترة.
- DNS: صلاحية تحرير DNS فقط لمن يدير النطاق.
- R2: حصر القراءة/الكتابة في bucket `datetools-media` متى سمحت آلية Token بذلك.
- النشر الآلي: Token مستقل بأقل صلاحيات Workers/Routes المطلوبة، دون صلاحية الفوترة أو إدارة الأعضاء.
- التحقق: الأعضاء، الأدوار، API Tokens، الجلسات، سجل التدقيق، وعدم وجود Token قديم أو Global API Key مستخدم في CI.
- المرجع: [Cloudflare account roles](https://developers.cloudflare.com/fundamentals/manage-members/roles/).

### H-IAM-02 Firebase وGoogle Cloud

- الحالة: `[~]` اكتمل الفحص الخارجي بتاريخ 2026-09-19؛ بقيت قرارات المعالجة: مالك احتياطي، حساب خدمة أقل صلاحية، ومتغير بناء App Check واختباره قبل Enforcement.
- IAM: مالك بشري واحد فقط بدور `Owner`، ولا يوجد مالك احتياطي موثق.
- Service Accounts: حساب Firebase Admin SDK واحد مفعّل مع مفتاح مولد واحد نشط طويل الأجل.
- الاستخدام الفعلي: المفتاح مطلوب حاليًا لتوقيع OAuth والوصول الخادمي إلى Firestore؛ لم يُعثر على قيمة المفتاح في المستودع، وSecret Scan يحظر تسريب المفاتيح الخاصة.
- فجوة أقل صلاحية: الحساب الخدمي يحمل Firebase Admin SDK Administrator Service Agent وApp Check Admin وAuthentication Admin وService Account Token Creator، بينما الكود المرصود يطلب نطاق Datastore فقط ويتحقق من ID Tokens عبر مفاتيح Google العامة.
- الإجراء المقترح: حساب خدمة مستقل لخادم الموقع بصلاحيات Firestore الدنيا، اختباره، تدوير سر Worker، ثم تعطيل المفتاح القديم؛ لا ينفذ دون موافقة مستقلة وخطة رجوع.
- Authorized domains: النطاقان الافتراضيان لـFirebase و`date-tool.com` وبيئتا التطوير المحليتان `localhost` و`127.0.0.1` فقط؛ لا توجد نطاقات قديمة أو غير معروفة. يضاف `www.date-tool.com` فقط إذا بدأ OAuth منه مباشرة بدل تحويله إلى النطاق الأساسي.
- App Check APIs: كل من Cloud Firestore وAuthentication في وضع `Monitoring`، والطلبات المرصودة 0% موثقة و100% غير موثقة. يمنع تفعيل Enforcement قبل تسجيل تطبيق الويب ودمج موفر الحماية واختبار التدفقات حتى لا تتعطل المصادقة أو البيانات.
- App Check Apps: تطبيق الويب مسجل وحالته `Registered` مع `reCAPTCHA Enterprise`. الكود يهيئ App Check عند توفر `NEXT_PUBLIC_FIREBASE_APP_CHECK_SITE_KEY`، لكن الاسم موجود فقط في نموذج متغيرات التطوير ولا يظهر في إعداد Wrangler؛ يرجح أن متغير البناء غائب من Cloudflare. يوضع كمتحول Build عام دون حفظه في Git، ثم تنشر نسخة اختبار وتراقب نسبة الطلبات الموثقة قبل Enforcement.
- Authentication Usage: خطة المشروع `Spark` المجانية، والاستخدام الحالي منخفض ولا توجد بيانات استخدام SMS أو مؤشرات ضغط ظاهرة على الحصة. يلزم إكمال مراجعة Usage and Billing العامة والتنبيهات دون ترقية الخطة.
- Usage and billing: تكلفة المشروع `No-cost` على Spark. استهلاك Firestore المرصود بعيد عن الحدود اليومية: القراءة أقل من 1%، والكتابة والحذف شبه صفر. Spark يوقف المنتج عند تجاوز الحد بدل الفوترة، لذلك يبقى فحص Account & budgets مطلوبًا لتوثيق الارتباط والتنبيهات.
- Account & budgets: لا يوجد حساب فوترة أو ميزانيات لأن المشروع على `Spark No-cost`. لا توجد تكاليف أو تنبيهات مالية قابلة للضبط ما لم ينتقل المشروع مستقبلًا إلى Blaze؛ أي ترقية تحتاج موافقة مستقلة وحدود ميزانية وتنبيهات قبل التنفيذ.
- `Owner`: شخصان موثوقان كحد استمرارية، ولا يستخدم الدور للعمل اليومي إن أمكن.
- المشاهدة: `Viewer` أو أدوار قراءة المنتج.
- التشغيل: أدوار Firebase/Firestore/Auth/App Check المحددة بدل `Editor` العام.
- Service Account الخاص بالخادم: فقط العمليات التي تحتاجها واجهات الموقع، ولا يمنح Owner أو Editor.
- التحقق: IAM principals، الحسابات الخدمية ومفاتيحها، Authorized domains، App Check، الحصص، Billing، وعدم وجود عضو أو مفتاح قديم.
- المرجع: [Firebase IAM](https://firebase.google.com/docs/projects/iam/overview).

### H-IAM-03 GitHub

- الحالة: `[~]` اكتمل الفحص والتشديد التقني بتاريخ 2026-09-20؛ بقي قرار استمرارية الملكية فقط، لأنه يتطلب نقل المستودع الشخصي إلى Organization عند توفر مالك احتياطي موثوق.
- Collaborators: صفر متعاونين؛ الحساب المالك وحده يملك المساهمة والإدارة. لا توجد صلاحيات بشرية زائدة.
- استمرارية الملكية: المستودع شخصي، لذلك لا يمكن إضافة مالك حساب احتياطي. عند الحاجة لاستمرارية مؤسسية ينقل إلى Organization مع مالكين موثوقين وMFA إلزامي.
- Deploy keys: لا توجد مفاتيح نشر مرتبطة بالمستودع؛ لا يوجد وصول SSH خارجي مباشر للقراءة أو الكتابة.
- GitHub Apps: التطبيق المثبت الوحيد هو `Cloudflare Workers and Pages` المستخدم لتكامل البناء والنشر؛ يلزم فحص نطاق المستودعات والصلاحيات من صفحة Configure.
- Cloudflare GitHub App: الوصول محصور في مستودع `date_tools` فقط. يملك قراءة metadata وقراءة/كتابة administration وchecks وcode وdeployments وpull requests. الصلاحيات واسعة لكنها مرتبطة بالبناء والنشر التلقائي؛ يبقى التكامل ما دام مستخدمًا وتراجع ضرورته دوريًا.
- Actions secrets: لا توجد Repository secrets ولا Environment secrets؛ النشر لا يعتمد على مفاتيح محفوظة في GitHub Actions.
- Actions variables: لا توجد Repository variables ولا Environment variables؛ لا توجد إعدادات عامة قديمة أو غير موثقة في Actions.
- Actions permissions: `GITHUB_TOKEN` الافتراضي للقراءة فقط، وإنشاء/اعتماد Pull Requests معطل. CodeQL يمنح `security-events: write` داخل مهمته فقط لرفع النتائج.
- Actions policy: يسمح بالإجراءات الخارجية، لكن GitHub يشترط الآن تثبيت كل Action على commit SHA كامل. جميع الإجراءات الرسمية المستخدمة في workflows المحلية مثبتة على SHA كامل مع تعليق الإصدار.
- Fork workflows: الموافقة مطلوبة لأول مساهمة فقط، وليست لكل مساهم خارجي. المخاطرة محدودة حاليًا لعدم وجود أسرار ولأن الرمز للقراءة، لكنها تراجع مع سياسة الفروع.
- Branch protection: Ruleset نشط باسم `Protect master` يستهدف الفرع الافتراضي؛ يمنع حذف الفرع وforce-push، ولا يفرض Pull Request أو status checks حتى لا يعطل الدفع والنشر العاديين.
- Organization Owner: شخصان موثوقان عند استخدام Organization.
- Repository Admin: فقط من يحتاج إعداد الأمان والفروع والأسرار.
- Maintain: إدارة المشروع دون صلاحيات حساسة أو حذف.
- Write: من يرفع الشيفرة فقط. Triage/Read للدعم أو المراجعة دون كتابة.
- Actions: `GITHUB_TOKEN` للقراءة افتراضيًا، وتضاف كتابة محددة للعمل الذي يحتاجها فقط.
- التحقق: Collaborators/Teams، Deploy keys، GitHub Apps، PATs، Actions secrets، Branch protection، وسجل التدقيق.
- المراجع: [Repository roles](https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization) و[Organization roles](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/roles-in-an-organization).

### H-IAM-04 AdSense وGoogle Payments

- الحالة: `[x]` اكتملت مراجعة المستخدمين بتأكيد المالك بتاريخ 2026-09-20؛ يوجد الحساب الأساسي النشط فقط بمستوى وصول `Admin`، ولا توجد حسابات قديمة أو صلاحيات بشرية زائدة.
- الاعتماد على حساب واحد مقبول حاليًا بقرار المالك، مع توثيق أن استمرارية الوصول تعتمد على وسائل الاسترداد المحمية للحساب الأساسي.
- `Admin`: المالك الأساسي ومالك احتياطي موثوق فقط؛ يستطيع إدارة المستخدمين والشروط وإغلاق الحساب.
- `Standard`: من يدير الإعلانات والتقارير ولا يحتاج إدارة المستخدمين أو إغلاق الحساب.
- Payments: فقط المالك أو مسؤول مالي محدد، ولا تُشارك بيانات الدفع مع مدير المحتوى أو الإعلانات.
- عند إضافة مستخدم مستقبلًا: يمنح `Standard` افتراضيًا، ولا يمنح `Admin` إلا لمن يحتاج إدارة المستخدمين والشروط وإغلاق الحساب.
- المرجع: [AdSense user access](https://support.google.com/adsense/answer/2646544).

### H-IAM-05 Search Console

- الحالة: `[x]` اكتملت مراجعة المستخدمين بتأكيد المالك بتاريخ 2026-09-20؛ يوجد الحساب الأساسي فقط بصلاحية `Owner`، ولا يوجد مالك سابق أو مستخدم إضافي.
- الاعتماد على مالك واحد مقبول حاليًا بقرار المالك، مع بقاء استمرارية الوصول مرتبطة بحماية حساب Google وإثبات ملكية النطاق.
- `Verified owner`: يبقى إثباته تحت سيطرة مالك النطاق، ويفضل وجود مالك موثوق ثانٍ.
- `Delegated owner`: فقط من يحتاج إدارة المستخدمين والإعدادات.
- `Full user`: مختص SEO الذي يحتاج التقارير وطلب التحقق.
- `Restricted user`: قراءة محدودة لمن لا يحتاج تنفيذ إجراءات.
- عند إضافة مختص مستقبلًا: يمنح `Full` أو `Restricted` حسب حاجته، ولا يمنح `Owner` إلا عند الحاجة الفعلية لاستمرارية الملكية.
- المرجع: [Search Console users and permissions](https://support.google.com/webmasters/answer/7687615).

### H-IAM-06 أدوار المنصة الداخلية

- الحالة: `[~]` النموذج البرمجي موجود، والمراجعة التفصيلية مؤجلة بقرار المالك بتاريخ 2026-09-20 لعدم وجود سوى الحساب الأساسي. يعاد الفحص قبل إضافة أول مدير أو مساعد أو معلن فعلي.
- `platform_owner`: ملكية المنصة ونقلها فقط، ويستخدم بأقل قدر ممكن.
- `super_admin`: إدارة عامة دون نقل الملكية أو حذف المالك.
- الأدوار المتخصصة: تشغيل، محتوى وSEO، إعلانات، حسابات معلنين، أمن، دعم، أداء، تدقيق للقراءة، ومساعد بصلاحيات صريحة.
- المطلوب: لا يُمنح `super_admin` لمهمة يستطيع دور متخصص تنفيذها، ولا يمنح المساعد أي صلاحية ضمنية.
- شرط إعادة الفحص: قبل تفعيل أي حساب جديد، يراجع دوره ونطاقه وحالة MFA وسجل الدعوة، مع إبقاء الحساب الأساسي وحده بدور `platform_owner`.

## اختبار الملفات والوسائط

المقصود بـ"ملف تنفيذي" ملف يستطيع تشغيل أوامر أو شيفرة، مثل `.exe`, `.msi`, `.bat`, `.cmd`, `.ps1`, `.js`, `.html` أو SVG يحتوي أحداثًا/JavaScript. لا نستخدم برمجية ضارة حقيقية في الاختبار.

### H-UPLOAD-01 صورة سليمة

- الحالة: `[~]` نجح اختبار التكامل المعزول بتاريخ 2026-09-20: قبل صورة PNG سليمة، استدعى Bucket الوهمي مرة واحدة، وأنشأ مسارًا وبيانات وصفية آمنة وسجل تدقيق. بقي اختبار واجهة بالحساب التجريبي.
- ارفع PNG أو JPEG صغيرة غير حساسة.
- المتوقع: تقبل، يظهر النوع الصحيح، ولا يظهر مفتاح R2 الداخلي.

### H-UPLOAD-02 امتداد صورة مزور

- الحالة: `[~]` الرفض البرمجي واختبار التكامل المعزول مثبتان؛ لم يُستدعَ التخزين أو سجل التدقيق. بقي اختبار الواجهة يدويًا بالحساب التجريبي.
- ينشئ Codex ملف نصي غير مؤذٍ باسم `fake-image.jpg`.
- المتوقع: يرفض بسبب Magic Bytes؛ وهي التوقيع الحقيقي داخل الملف، لا اسم الامتداد.

### H-UPLOAD-03 HTML وSVG نشط غير مؤذي

- الحالة: `[~]` رفض HTML وSVG النشط قبل التخزين مثبت باختبار تكامل مع Bucket وهمي؛ بقي اختبار الواجهة يدويًا بالحساب التجريبي.
- ينشئ Codex ملفي اختبار محليين يحتويان نصًا/حدثًا واضحًا دون حمولة ضارة.
- المتوقع: يرفضان، لا ينفذ أي كود، لا يُنشأ رابط عام، ولا يبقى ملف جزئي في R2.

### H-UPLOAD-04 ملف تنفيذي

- الحالة: `[~]` رفض Fixture تنفيذي آمن قبل التخزين مثبت باختبار تكامل معزول؛ بقي اختبار الواجهة يدويًا بالحساب التجريبي.
- لا ننشئ ولا نشغل ملفًا تنفيذيًا حقيقيًا؛ نستخدم Fixture آمنًا بتوقيع وهمي وامتداد محظور.
- المتوقع: رفض قبل التخزين، ورسالة عامة لا تكشف مسار الخادم.

ضوابط إضافية مثبتة آليًا: حد 5 MiB، أبعاد موجبة بحد أقصى 8192 لكل ضلع و40 مليون بكسل، قراءة أبعاد PNG وJPEG وWebP وGIF وICO، منع المسارات غير المعروفة، وتقييد المعلن بفئة `ads` وبأدوار تعديل الحملات فقط.
