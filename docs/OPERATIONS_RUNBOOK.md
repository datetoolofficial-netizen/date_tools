# دليل تشغيل واستعادة date_tools

هذا الدليل يحدد ما يجب فحصه عند تعطل الموقع، وكيفية الرجوع إلى نسخة سابقة، وما الذي يحتاج خدمة خارجية مدفوعة. لا يحتوي أسرارًا أو معرفات حسابات شخصية.

## المصطلحات

- **Health check (فحص الصحة):** طلب آلي صغير يتأكد أن الموقع وواجهات الخدمة الأساسية تستجيب بالمحتوى المتوقع، وليس مجرد أن النطاق يفتح.
- **SLI (مؤشر مستوى الخدمة):** القياس الفعلي، مثل نسبة الطلبات الناجحة أو زمن الاستجابة.
- **SLO (هدف مستوى الخدمة):** الهدف المطلوب للمؤشر، مثل نجاح 99.9% من الطلبات خلال شهر.
- **RPO (هدف نقطة الاستعادة):** أقصى مدة بيانات نقبل فقدها عند حادث. RPO مقداره 24 ساعة يعني احتمال فقد آخر 24 ساعة من التغييرات.
- **RTO (هدف زمن الاستعادة):** المدة المستهدفة لإعادة الخدمة بعد الحادث.
- **Rollback (الرجوع):** إعادة Worker إلى نسخة منشورة سابقة عندما تسبب النسخة الجديدة عطلًا.

## مسؤولية الحوادث

- المسؤول الأول: حساب الإدارة ذي الدور القانوني `platform_owner`.
- لا توضع كلمات المرور أو مفاتيح Cloudflare أو Firebase في تذكرة الحادث أو Git أو لقطات عامة.
- قبل أي تعديل إنتاجي، يسجل المسؤول: وقت البداية، الأعراض، آخر نسخة سليمة، القرار، والنتيجة.

## مستويات الحوادث

| المستوى | المثال | بدء الاستجابة | القرار الأول |
|---|---|---:|---|
| حرج P1 | الموقع أو الدخول متوقف، تسرب أو اشتباه اختراق | 15 دقيقة | عزل السبب أو الرجوع فورًا |
| عال P2 | أداة أساسية أو الإعلانات أو Firebase تتعطل جزئيًا | 60 دقيقة | تعطيل الميزة المتأثرة أو الإصلاح |
| عادي P3 | خلل بصري أو وظيفة غير حرجة | يوم عمل | إدراجه في إصدار مختبر |

## فحوص الصحة المحلية

شغل التطبيق محليًا أولًا:

```powershell
npm run dev -- --hostname 127.0.0.1 --port 3000
npm run health:check -- http://127.0.0.1:3000
```

يفحص الأمر خمسة مسارات: `/api/health`، نسخة التطبيق، Manifest، robots، وخريطة الموقع. نقطة `/api/health` تعرض اسم الخدمة والنسخة والوقت فقط ولا تكشف البيئة أو الأسرار.

بعد نشر مصرح به فقط، يمكن فحص النطاق نفسه:

```powershell
npm run health:check -- https://date-tool.com
```

بعد كل نشر مصرح، شغّل الفحص الموسع التالي. لا ينشر هذا الأمر أي شيء؛ ينتظر انتشار النسخة ويتحقق من مطابقة رقمها في `package.json` ومن اللغتين والمسارات الحرجة وملفات SEO وPWA و`ads.txt`:

```powershell
npm run health:production
```

يمكن تشغيل الفحص نفسه من GitHub Actions عبر `Post-deploy health`، أو استدعاؤه من مسار نشر مستقبلي باستخدام `workflow_call` أو حدث `production-deployed` مع رقم النسخة.

## أهداف الخدمة الأولية

هذه أهداف تشغيلية أولية وليست ضمانًا تعاقديًا:

- الصفحة العامة وواجهات القراءة الأساسية: توفر شهري 99.9%، ونسبة أخطاء خادم أقل من 0.5%.
- دخول الإدارة والمعلنين: نجاح 99.5% من المحاولات الصحيحة، مع فصل أخطاء المستخدم عن أعطال الشبكة والخدمة.
- فحص الصحة: ينجح كل خمس دقائق، وينبه بعد فشلين متتاليين لتجنب إنذار عابر.
- الرحلات الحرجة: فتح الموقع، الدخول، قراءة الإعداد العام، وفتح صفحة أداة مستقلة.

Cloudflare Health Checks والتنبيهات الخارجية تحتاج إعدادًا من الحساب، وقد تتطلب خطة Pro أو أعلى. هذا الإعداد الخارجي غير منفذ محليًا.

## RPO وRTO

| الأصل | RPO المستهدف | RTO المستهدف | الوضع الحالي |
|---|---:|---:|---|
| كود الموقع والقواعد والإعدادات غير السرية | صفر تغييرات ملتزم بها | 30 دقيقة | محفوظة في Git ويمكن بناء نسخة سابقة |
| Cloudflare Worker | آخر نسخة منشورة سليمة | 30 دقيقة | الرجوع متاح من إصدارات Worker |
| Firestore | 24 ساعة | 4 ساعات | يحتاج Scheduled Backups وتجربة استعادة على مشروع منفصل؛ خدمة مدفوعة |
| صور R2 المهمة | 24 ساعة | 8 ساعات | يحتاج سياسة نسخ/إصدارات وتجربة استعادة خارجية |
| الأسرار | لا تخزن في Git | 4 ساعات | تستعاد من مدير أسرار أو تعاد تهيئتها يدويًا |

## خطوات التعامل مع حادث

1. لا تنشر إصلاحًا تجريبيًا مباشرة. سجل الوقت والمسار ورسالة الخطأ ورقم النسخة.
2. شغل فحص الصحة وحدد هل العطل عام أم خاص بمسار أو خدمة خارجية.
3. راجع Cloudflare Worker Logs وFirebase دون نسخ Token أو بيانات شخصية.
4. إذا بدأ العطل بعد نشر وكان أثره P1، ارجع إلى آخر Version ID سليم.
5. تحقق من الصفحة و`/api/health` والدخول والمسار المتأثر بعد الرجوع.
6. اكتب السبب والإصلاح والاختبار الذي يمنع التكرار قبل إعادة النشر.

## الرجوع إلى Worker سابق

عرض الإصدارات واختيار نسخة سليمة يتم من Cloudflare Dashboard أو Wrangler. أمر الرجوع لا يستخدم إلا بموافقة نشر صريحة:

```powershell
npx wrangler rollback <VERSION_ID> --name datetools --message "سبب الرجوع"
```

الرجوع يعالج كود Worker، لكنه لا يعيد بيانات Firestore أو ملفات R2. عند وجود تغيير بيانات غير متوافق يلزم اتباع خطة ترحيل مستقلة قبل الرجوع.

## بوابة الجودة قبل أي نشر

```powershell
npm run quality:local
```

تشمل ESLint، فحص ثغرات تبعيات الإنتاج، اختبارات الوحدة، اختبارات صلاحيات Firestore على Emulator محلي، بناء Next.js، ثم رحلات Playwright والوصول. نجاحها لا ينشر شيئًا.

## العناصر الخارجية المتبقية

- تفعيل Cloudflare Health Checks والتنبيهات وربط جهة اتصال ثانية.
- تفعيل Firestore Scheduled Backups أو PITR بعد اعتماد التكلفة، ثم تجربة الاستعادة إلى مشروع منفصل.
- اعتماد نسخة احتياطية لصور R2 واختبار سلامة الروابط بعد الاستعادة.
- جمع تقارير CrUX وSearch Console وAdSense بعد مرور مدة كافية على الإنتاج.
- اختبار التثبيت والتحديث وقارئ الشاشة على أجهزة حقيقية وفق خطة القبول.
